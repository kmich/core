# Native Clustering for Home Assistant (Single-Leader Warm Standby)

Native active/passive high-availability clustering for Home Assistant Core, coordinated through **NATS JetStream**.

Two or more Home Assistant installations with matching configuration form a cluster. One node is elected **Leader** and runs the clustered config entries, automations, scripts and YAML platforms. The other nodes remain on **Warm Standby**: they mirror the leader's states of clustered entries, forward service calls to it, and take over once the leader's lease expired or was released. Each node is still its own installation: per-node work (excluded domains, every-instance integrations, top-level YAML integrations, its own users) keeps running on every node. See [Known limitations](#6-known-limitations).

---

## 1. Architectural Overview

```
                          +------------------------+
                          |     NATS JetStream     |
                          | (hass_leases, states,  |
                          |     hass_storage)      |
                          +-----------+------------+
                                      ^
                                      |
                 +--------------------+--------------------+
                 |                                         |
                 v                                         v
     +-----------------------+                 +-----------------------+
     |      LEADER NODE      |                 |     STANDBY NODE      |
     |                       |                 |                       |
     | - Holds '_leader'     |  State Mirror   | - No leases held      |
     | - Runs Integrations   | ==============> | - Warm UI Visibility  |
     | - Automations/Scripts |                 | - Read-only states    |
     | - Publishes records   | <============== | - Forwards service    |
     | - Publishes to KV     |  RPC Forwarding |   calls to Leader     |
     +-----------------------+                 +-----------------------+
```

### Why Single-Leader Warm Standby?

Earlier prototypes attempted per-integration active/active partitioning (where Node A ran Z-Wave and Node B ran Zigbee). In practice, active/active introduces fatal edge cases in Home Assistant:
1. **OAuth2 / Token Rotation:** Token updates on one node fail to synchronize before failover, leaving the next owner with stale tokens.
2. **Registry Clashes:** Both nodes modifying entity/device registries leads to ID divergence or split-brain file writes.
3. **Cross-Entity Automation Splitting:** Evaluating triggers and conditions across nodes causes event latency and race conditions.

The **Single-Leader Warm Standby** design is meant to avoid these problems; it does not remove every way they can happen (see [Known limitations](#6-known-limitations)):
* Only the **leader** runs the integrations of clustered config entries, and only the leader publishes config entry records and the mirrored stores (registries, restore state) to JetStream. The NATS server refuses writes from a leader whose term another node has superseded (see [Fenced storage writes](#8-fenced-storage-writes)).
* Standby nodes stay warmed up: the states of clustered entries are mirrored into memory. A standby's config entries follow the leader's (added, removed, disabled, subentries), and it loads the leader's registries when it takes over, so entity ids, device ids and areas usually survive a failover.
* When failover occurs, the promoting standby adopts the latest published records of the entries it already has and sets them up again. The end-to-end harness measured a median of 4.9 s (4.6 to 7.7 s over 10 runs) from a network cut to the first state of one `sun` entry on the new leader (see [Failover time](#failover-time)); this is not a bound for other integrations.

## 2. Component Modules

The cluster is part of Core, not an integration: `homeassistant/cluster/` has no manifest, and bootstrap sets it up from the `cluster:` key before any integration (an unconfigured instance never imports it). The NATS client is the optional package `nats-py` (`pip install homeassistant[cluster]`); without it, or with an invalid `cluster:` section, clustered config entries stay unloaded. The cluster relies on hooks in Core (placement of config entries, the service router, the store write listener, registry and collection replacement, leader-only YAML platforms, automations and scripts, and `helpers/cluster.py`). Three methods of Core objects exist for the cluster only and are underscore names that the cluster package calls with `# noqa: SLF001`: `ConfigEntries._async_remove_replica` (remove an entry that another instance removed and cleaned up), `ConfigEntries._async_set_standby` (say why an unloaded entry runs elsewhere) and `ServiceRegistry._async_call_local` (the body of `async_call`, past the router; it takes an optional set that receives the task of a non-blocking call until it ends). Without a cluster none of them is called. The cluster package also calls `ServiceRegistry._async_call_local` from `ui_config_sync.py` (the reload of a file it wrote), and reaches into `RestoreStateData._async_load_stored_states` (`storage_sync.py`) and `BaseRegistry._store` (`registry_sync.py`, to read the storage version). Neither is a hook.

## 3. Safety Mechanisms and Their Limits

The goal is that clustered work runs on one node at a time. The mechanisms below make overlap unlikely; they are software mechanisms inside Home Assistant and do not give a hard guarantee (see [Limits](#limits) at the end of this section).

### 1. Loop-Timer Fencing (`ttl - margin`)
A leader measures elapsed monotonic time from the moment it sent its last successful renewal. If it does not renew `_leader` within `fence_after` (2.4 s on a 3.0 s lease), it **fences itself locally**: it stops acting as leader, detaches automation triggers, stops script runs, takes down YAML platforms and unloads its clustered entries. The leadership flag (`async_is_leader`) also expires at that deadline on its own, even while the event loop is stalled.

### 2. Clean Release and Unload Grace
A node deletes `_leader` (a *clean release*) only if nothing that runs on the leader only still runs on it: no clustered entry (also a disabled one that is still unloading) is in any state but `NOT_LOADED` or `MIGRATION_ERROR` (so also one that waits for a setup retry or failed), no forwarded service call is running (a non-blocking call counts until its service has ended, not only until it was answered), no unload failed, and the work a demotion started (stopping automation and script runs, taking down YAML platforms, the clean-up of a removed entry) has finished and did not fail. Otherwise it stops renewing and lets the key expire.

When a standby takes `_leader`:
* After a clean release, it writes over **exactly the delete marker it read** (compare-and-set on that revision) and takes over without a grace. Any other write after the release (another node's whole term, or the key expiring) makes that write fail, and the standby looks again.
* In every other case it waits `lease_ttl + grace` after it last saw the old leader renew (or after it started to watch the bucket), while it renews its own lease. `grace` is the largest `unload_grace` of this node and of any node that advertised one in its lease or member key, so a node with a shorter grace still waits for one with a longer one.

### 3. Demotion Waits for Setups in Progress
Demotion takes each entry's `setup_lock`, so a setup in progress finishes and is then unloaded. A YAML platform is counted before its first await: a demotion waits for platforms that passed the leadership check and then takes them down, and a platform that finds leadership gone once it is loaded does not set up.

### 4. Restart on `FAILED_UNLOAD`, and the stop watchdog
If an integration fails to unload during demotion, the node leaves the lease to expire (no clean release) and restarts Home Assistant (`LeaseManager.async_restart`, exit code 100).

Quiescence is recorded, not inferred. Work that stops leader-only activity registers itself in `helpers/cluster.py` and counts until it finished: a platform teardown, a stop of automation or script runs, and the clean-up of a removed config entry (which Core already dropped from its table). Work that raised or was cancelled, an entry whose unload failed, and an entity whose removal raised stay pending for the rest of the process, so the lease is not released cleanly and the watchdog stays armed.

A restart can itself hang, and the event loop can stall. A **watchdog thread** (`watchdog.py`) is armed whenever this node leads or still runs leader-only work. Every renewal moves its deadline to `renewal sent + lease_ttl + unload_grace - 0.3 s`; a non-leader that still runs a clustered entry gets `(lease_ttl - fence_after) + unload_grace` when it notices. It is disarmed only once nothing runs any more. When the deadline passes, the thread ends the process with `os._exit` (100, or the exit code of the stop during a shutdown). It does not log then (a log handler blocked on a slow disk holds the logging lock): it writes one line to stderr, gives its clean-up hooks (stopping managed add-ons through a detached helper process) 50 ms in a thread of their own, and ends the process whether they returned or not.

### 5. Shutdown
Before the stop event, a leader stops acting as leader, refuses to set up or remove clustered entries (admission is closed at once, not after the unload), and unloads its clustered entries (a shutdown job, so that integrations are unloaded while they still expect it). After the final write it publishes its records and releases the lease only if all that work stopped; otherwise the other nodes wait for the lease to expire, and the watchdog stays armed until the process ends.

Every node writes its unload grace to `grace.<node_id>` in the storage bucket at start and reads the others', so the grace of a holder whose lease key already expired is still waited for. A node that is removed from the cluster keeps its key until its name is used again; configure the grace equally on every node.

### 6. Duplicate `node_id` Protection
Each instance writes a unique UUID heartbeat to `_node.<node_id>`. If two nodes are mistakenly booted with the same `node_id`, the later instance stands down and remains standby until the other run's key is gone.

### 7. Automatic Health Handoff
If no gated config entry is loaded on the leader, at least one failed (`SETUP_RETRY` / `SETUP_ERROR`) and the others failed or are still setting up, for `max(2 * lease_ttl, 10 s)` (not configurable), and another node renews its member key, the leader steps down. A member key shows that the peer's process runs, not that the peer can run the entries. The step-down releases the lease cleanly only if every entry unloaded (see 2). While it unloads, the node stops renewing the lease: the unload has the lease and unload grace as its budget, and the watchdog ends the process if it hangs.

### 8. Fenced Storage Writes
Each new leader starts a **term** before it reads or writes anything in `hass_storage`: it increases the `cluster.term` key with a compare-and-set, and the revision of that write is its fencing token. Every write of the leader to `hass_storage` (entry records, removal announcements, tombstones, the inventory, mirrored stores, UI records, helper states, and their deletes) is conditional on that token (`Nats-Expected-Last-Subject-Sequence` with `Nats-Expected-Last-Subject-Sequence-Subject` naming the term key). Add-on snapshots are fenced writes too (as rollups: the bucket keeps one value of each chunk), so a superseded leader cannot replace the snapshot the next leader restores. Two writes are not: the term key itself (a compare-and-set on the revision that was read) and `grace.<node_id>`, which every node writes with a plain put at start. After another node started a term, the server refuses every write of the old leader, which then stops leading at once. A lost term key (the bucket recreated, or the key purged) is not another node's term: the leader starts a term again. The memory-backed state mirror (`hass_states`) is not fenced by the server. Every published state carries the term of its writer, a receiver drops a state of an older term, and a delete is conditional on the revision of the writer's own last write, so a superseded leader cannot remove a newer leader's state. A new leader also drops mirrored states at promotion.

### 9. Removals Survive a Failover
A leader announces a removal (an `entry.<id>` record with `removing`) before the integration's clean-up runs, and refuses the removal if it cannot. The tombstone (`removed`) follows once the entry is gone. The announcement carries the entry's record, so a node that never had a copy can still run the clean-up. A node that takes over and finds the announcement completes the removal itself, clean-up included (clean-ups must be repeatable), and never sets the entry up. The tombstone is written only if the clean-up did not raise, and only by a node that leads; otherwise the announcement stays (a node that does not lead keeps the removal and its intent until it can confirm it) and the next leader repeats it. The leader keeps the announcements of unfinished removals in its private store (saved at once) and publishes them again, before the inventory, when the storage bucket was recreated.

### 10. Protocol Version
`protocol` (`PROTOCOL_VERSION`, `1` today, in `const.py`) is written into every member key (`_node.<id>`), the leader lease, and every config entry record (entry records, removal announcements, tombstones) and the inventory, in the readable part next to `origin` and `term`. The registries, the UI files and the states carry no version of their own: a change to what they hold is a protocol change, and the member keys say so.

* **A key or record without the field is version 1.** Everything written before the field existed is that, so a cluster that already holds records upgrades without a purge. Only the integer of this node's version counts: `true`, `1.0`, `"1"` and any other number are another version.
* **A node does not take the lease while a node of another version is alive**, that is, while a member key or the lease of such a node was renewed within `lease_ttl + renew_interval`. The log says which nodes and versions, and the repair issue *Cluster node <id> cannot take over* (see below) is raised at once. The check comes before the lease is claimed. It is made again after the grace wait and once more before the node starts to lead (the handover can take seconds): a node that finds such a node then gives the lease back and waits out the cool-down. It ends by itself: a node that stops renewing is forgotten after that time (the server expires its keys without telling anyone), a node that is upgraded replaces its key.
* **A leader that sees such a node keeps leading.** Stepping down would leave nobody who can lead. Only a node that wants to *start* leading is blocked.
* **A record of another version is never applied.** A standby skips it and logs it once per key (and does not believe the term in it); a promotion stops with `HandoverIncomplete` naming the key, gives the lease back and raises the repair issue. The check runs before the record is decrypted or any of it is used.
* **What this does not cover.** Nodes from before this check do not look at versions; between them and newer nodes only the rule that every node runs the same version protects. The first protocol change must either be made so that both versions can be read for a while, or be rolled out by stopping every node. Version 1 has no such window.

### 11. Repair Issues When the Cluster Is Stuck
Four repair issues (`homeassistant` translations, raised from `helpers/cluster.py` so that they exist when the cluster package cannot be imported) say what the log says, where a user looks:

* **The cluster could not be set up** (`cluster_setup_failed`): the packages could not be installed, `nats-py` cannot be imported, or the `cluster:` section is invalid (the issue names the key that is wrong, not its value; the log has the message). Entries of clustered domains stay unloaded. Not raised when NATS cannot be reached: that is retried in the background and the entries wait (see the next issue for a server that was reached and refused). The issue is removed when the cluster is set up, or when `cluster:` is gone from the configuration.
* **The cluster's NATS server was refused** (`cluster_connection_refused`): the node reached a server and refuses it, or the server refuses the node, for a reason that waiting does not fix: strict mode and a server without TLS or a user that may publish as any node, a certificate the node does not trust (`ca_file`), credentials the server rejects, a server older than 2.15. The issue names the reason (never a URL or a credential). The node keeps trying in the background, with growing pauses, so fixing the server or the user is enough; the issue is removed when a connection is accepted. A server that is down or not reachable is not reported here. The first connection fails at once with the reason (the TLS or the authorization error) instead of retrying until its timeout; with several servers it fails once every server has refused. An established connection still reconnects for ever.
* **A cluster node cannot take over** (`cluster_cannot_take_over`): raised at once when a promotion stops because a handover cannot be completed (a record cannot be read, applied or is of another version, NATS is not reachable) or because of a node of another protocol version, and after 3 promotions in a row that raised. The issue names the reason; removed by the next promotion of this node that succeeds, or when the node of another version is gone. After a failed promotion a node waits at least 60 seconds before it tries again, so three failures take a few minutes.
* **Cluster nodes run different Home Assistant versions** (`cluster_version_mismatch`, a warning): a live node reports another `ha_version`. It names the nodes and versions, and does not stop anything. Removed when the versions agree again or the other node stops renewing its key.

### Limits
* The fence and the watchdog run inside the Home Assistant process. Code that holds the GIL, or a suspended process or VM, can delay them past the deadline (the watchdog does not log once its deadline passed, so a blocked log handler does not hold it up). A deployment that needs a hard guarantee needs a fence outside the process: a supervisor or hypervisor that stops the old node, or devices that accept commands of one node only.
* Nothing can take back what an external system (a device, a cloud API) already accepted from the old leader before it stopped.
* Who sent an RPC call or an event, and whose member key is whose, rests on NATS permissions (see [Securing the NATS server](#securing-the-nats-server)). Within those permissions every member can still write `hass_storage` and use the JetStream API: the term fencing stops a stale leader, not a compromised node.

## 4. Configuration

The cluster needs a NATS server **2.15 or later** with JetStream enabled; a node refuses to start with an older one.

Add the `cluster:` key to your `configuration.yaml` on all nodes:

```yaml
cluster:
  node_id: node_a                           # Required, unique per node ([A-Za-z0-9_-])
  nats_url: tls://nats-1:4222               # NATS JetStream server or cluster URL
  nats_user: node_a                         # This node's own NATS user (or nats_creds). A shared token is not accepted in strict mode
  nats_password: !secret nats_node_a
  encryption_key: !secret cluster_key       # The same on every node; required in strict mode (see below)
  # security: strict                        # Default; "permissive" allows no TLS and no credentials
  replicas: 1                               # JetStream replicas: 1, 3 or 5 (1 for a single NATS server, 3 for a NATS cluster)
  lease_ttl: 3.0                            # Lease TTL in seconds (default: 3.0)
  renew_interval: 1.0                       # Renewal tick interval in seconds (default: 1.0)
  unload_grace: 2.0                         # Seconds a new leader waits for the old one to unload (default: 2.0)
  rpc_timeout: 60.0                         # RPC service call timeout in seconds (default: 60.0)
  exclude_domains:                          # Integrations that always run locally on every node
    - zha
  skip_addons:                              # Managed add-ons this node never starts (e.g. low memory)
    - a0d7b954_vscode
  # nats_token: ...                         # Accepted only with security: permissive (a shared token cannot tell the nodes apart)
  # nats_ca: /config/nats-ca.pem            # CA file of the server's certificate, if it is not a public one
  # managed_addons:                         # Supervisor add-ons that run on the leader only (see "Supervisor add-ons")
  #   - all                                   # Every installed add-on but the local ones
  #   - slug: 45df7312_zigbee2mqtt            # Settings of one add-on
  #     exclude: zigbee2mqtt/log              # Not moved with it
  #     # paths: zigbee2mqtt                  # Its folders of the configuration folder (default: those its options name)
  #     # seed_node: node_a                   # Whose copy counts while the cluster has no snapshot of it
  #     # replicate: false                    # Only started and stopped, never snapshotted
  # local_addons:                             # Add-ons that run on every node (SSH, Samba and the editors already do)
  #   - a0d7b954_tailscale
  # addon_seed_node: node_a                   # Whose copies count while the cluster has no snapshots
  # addon_backup_location: nas_backups        # A Supervisor network storage for the add-ons' backups (large add-ons)
  # addon_snapshot_interval: 900              # Seconds between snapshots of the replicated add-ons
  # addon_takeover_wait: 90                   # Seconds a new leader waits for a node that ran an add-on and went silent
  # storage_exclude:                        # Mirrored stores this node does not publish, for example core.restore_state
  #   - core.restore_state
```

### The encryption key

`encryption_key` is a secret that every node holds and the NATS server never sees. Make one (at least 32 characters; a passphrase is refused, the key is not stretched):

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
```

and keep it in `secrets.yaml` on every node. `security: strict` requires it; without it (`permissive`) entry records are published as they are, and the node logs a warning at start.

* A record is bound to its bucket key (`entry.<id>`) and carries a non-secret id of the key that sealed it. A node refuses to read a record of another key (the message names both ids), a record that was damaged or moved to another key, an encrypted record when it has no key, and a plain record when it has one (no downgrade). Such a record is **not** skipped like a record with wrong content: a promotion stops with that message, because the node would otherwise lead with its own, older copy of the entry.
* **Changing the key, or turning it on for an existing cluster:** stop every node, delete the `hass_storage` bucket on the NATS server (`nats stream rm KV_hass_storage`; the nodes create it again), set the new key on every node, start them. Every node keeps its own copy of its entries, so nothing is lost; the first leader publishes them again under the new key (a test of the procedure checks this, including that the old key reads nothing left over, and that the second node reads the new records and takes over). Expect the repair issue *Cluster data was lost* on a node that had seen the cluster's inventory: the bucket is gone, and the node says so; nothing needs to be done, and it is removed when that node next takes over and finds the inventory. Until the first leader has published, no node with the new key can take over, which is why all nodes are stopped. A node that is started with the new key while the old records are still there refuses them, and its promotion stops (the message names both key ids).
* The key protects the records on the NATS server and in its backups. A member of the cluster has the key, so it is **not** a boundary between members: every member is trusted (see *The NATS deployment is part of the trust boundary* in the limits).

### Securing the NATS server

With `security: strict` (the default) a node refuses to start without NATS credentials of its own (`nats_user` and `nats_password`, or `nats_creds`; a token shared by all nodes cannot tell them apart), and without TLS unless the server is on a loopback address. It also checks what it connected to: the connection must really be encrypted (nats-py upgrades a `tls://` connection only if the server offers TLS, so a server without TLS is refused), and the node's NATS user must not be allowed to publish as another node (a probe on a subject of a node that does not exist; a user that may is refused). A server with a certificate of your own authority needs `nats_ca` (the file of that authority). Every node gets its **own** NATS user, in an account of its own cluster (subject and bucket names are fixed), with permissions that let it publish only under its own name:

* RPC calls to `hass.rpc.<to>.from.<node>` and events to `hass.event.<node>`; the receiver takes the sender from the subject, so a node cannot speak for another.
* Its own member key `$KV.hass_leases._node.<node>`, the leader key, and the `hass_states` and `hass_storage` buckets.
* Replies come to `_INBOX.<node>.>`, the only inbox it may subscribe to (`allow_responses` lets it answer the calls it receives).

[`tests/cluster/harness/nats-permissions.conf`](../../tests/cluster/harness/nats-permissions.conf) is a complete server configuration for two nodes; `tests/cluster/test_permissions.py` runs a cluster against it. Add the server's TLS settings (`tls { cert_file: ..., key_file: ... }`) for a deployment.

A forwarded call runs on the leader as its system user of the caller's role (admin, user or read-only): users exist per node, so a user id from another node is not used. Calls without a user (an integration's own) stay without one. A node runs at most 32 forwarded calls at once and answers more with "busy". Forwarded calls and calls made on the leader itself (its UI, its API, its automations) are work of the leader: while one runs, the lease is not released cleanly, and when leadership ends they get the unload grace to finish and are then cancelled (the caller of a cancelled call gets an error).

### Supervisor add-ons (apps)

On HA OS or a supervised installation, add-ons (apps) run next to Home Assistant: the Mosquitto broker, Zigbee2MQTT, Music Assistant, Node-RED, ESPHome, Matter Server, databases. In a cluster they must move with the leader. Two rules matter more than anything else here, and Zigbee2MQTT shows both: **two instances of one add-on can harm what they control** (two Zigbee2MQTT on one coordinator corrupt the network), and **an add-on that starts without its data can be worse than one that does not start** (a Zigbee2MQTT without the network's data forms a new network on the coordinator: zigbee-herdsman does so when the configured network does not match the adapter and there is no matching coordinator backup, and every device has to be paired again). `managed_addons` handles both, for any add-on:

* **Which add-ons.** `managed_addons: all` manages every add-on installed on the leader, and every add-on the cluster's index names (the restore installs one that a node does not have), except the **local add-ons**: tools for the host itself that run on every node. `core_ssh`, `a0d7b954_ssh`, `core_samba`, `core_configurator` and `a0d7b954_vscode` are local without configuration; `local_addons` adds more (Tailscale, Glances). An add-on whose host name is a server of `nats_url` (a NATS server that runs as an add-on) is local too: the cluster depends on it. Items next to `all` give an add-on settings of its own; a list without `all` manages the named add-ons only. Add-ons start in the order of their startup stage (`initialize`, `system`, `services`, `application`, `once`, as Supervisor starts them: Mosquitto before Zigbee2MQTT), then as named. An add-on that cannot start (no snapshot, a restore that fails) does not hold up the others; it is tried again every 30 s. The list is read again every minute on the leader and with each standby check, so an add-on installed later is managed from then on.
* **One node at a time.** Each node reports, in its member key, the managed add-ons that may run on it (one counts as running until Supervisor said it is stopped, and stays reported if Supervisor would not stop it). A new leader starts an add-on only once no live node reports it, and waits `addon_takeover_wait` (90 s) for a node that ran it and stopped reporting: a dead host and a dead Home Assistant on a live host look the same from outside, and in the second case the add-on still runs there until that Home Assistant is back (as a standby it stops the add-ons first thing). A node that started less than `addon_takeover_wait` ago waits as long, because a node that went away before it started never reported to it. A live node that keeps reporting an add-on for 2 minutes raises the repair issue. Standbys stop managed add-ons, set them to manual boot (Supervisor would otherwise start them with the host, before Home Assistant runs), and check every 30 s that they stay stopped. A leader that stops leading stops them at once. When the watchdog ends a hung process, it starts a detached helper process that asks Supervisor to stop them, and ends the process without waiting for it (best effort: the helper may not finish if the container goes down with Home Assistant; the node stops them again when it starts).
* **Only with the cluster's data.** A replicated add-on (the default) is started only after this node restored the cluster's latest snapshot of it, or if its local data is that snapshot (it made or restored it). The restore runs with the add-on stopped: its folders of the configuration folder are replaced whole (the old ones are kept aside, and put back if Supervisor's part of the restore fails, so the two never mismatch), Supervisor restores its own backup of the add-on (its `/data`, options and `addon_config` folder; a different add-on version is installed then, which takes as long as the download), boot is set to manual again, then it is started and must report started. A snapshot that cannot be read, is damaged, or was sealed with another key is never applied: the add-on stays stopped, the repair issue *Add-on … is not started on the cluster leader* says why, and the leader tries again.
* **The first snapshot.** While the cluster has no snapshot of an add-on, the node whose local data becomes the cluster's copy (the *seed*) must be clear; every other node refuses, and the leader raises the repair issue saying which node to let lead. In this order: an item's own `seed_node`; the node the cluster's index names as holding the data (an add-on that only that node had installed when the leader looked: its copy is never replaced by an empty install elsewhere, which for Zigbee2MQTT would form a new network); `addon_seed_node`, the node whose copies count for every add-on it has installed (set it to the host the add-ons ran on before the cluster, and make that node the leader once: start it first, or stop the others); and, without any of these, the leader for an add-on that is new to the cluster (not in its index) and that no other node reports installed. Each node reports the add-ons it has installed in its member key; the last report of a node that went away still counts.
* **Data in the configuration folder.** Some add-ons keep their data in Home Assistant's configuration folder instead of their own (Zigbee2MQTT in `zigbee2mqtt`, its default `data_path`; older ESPHome in `esphome`). Their Supervisor backup does not hold it. The cluster takes the folders an add-on's options name (a value such as `/config/zigbee2mqtt` or `/homeassistant/zigbee2mqtt`), except Home Assistant's own (`.storage`, `custom_components`, `blueprints`, `www`, `themes`, `packages`, ...). An add-on that uses a fixed folder without naming it in an option needs `paths`; `exclude` leaves out what need not move (`zigbee2mqtt/log`). The list of folders travels inside the encrypted snapshot, and a restore writes only those. A folder listed in an item's `paths` that the snapshot's node did not have (deleted there) is removed on the node that restores, so no stale copy stays next to the restored data; only a folder is removed, never a file, and never one only taken from the add-on's options.
* **Snapshots.** The leader snapshots each add-on it started every `addon_snapshot_interval` (15 minutes), while it runs, and once more, stopped, at a planned handover (a shutdown or restart of the leader), before it releases the lease. That final snapshot runs in Core's stop stage, which waits up to 100 s for its tasks (the handover takes at most 80 s), not in the shutdown jobs before it, which have 20 s for everything: the add-ons keep running through the resign until then. The lease is still held and renewed until the close event, so the snapshot is written in the leader's term. Through NATS a snapshot is the add-on's Supervisor backup (made and downloaded, then deleted on the host) and its folders, at most 64 MiB compressed, encrypted with `encryption_key` (required: a Zigbee network key or a broker's passwords are in there) and written in chunks below the server's `max_payload`. A recreated `hass_storage` bucket is snapshotted again at once. An add-on whose backup mode is cold (`backup: cold` in its configuration; Supervisor's API does not say which ones are) is stopped by Supervisor for every backup: give it `replicate: false`, a long `addon_snapshot_interval`, or accept the restarts.
* **Large add-ons: a network storage.** With `addon_backup_location` (the name of a network storage that Supervisor uses for backups, mounted on every node), the Supervisor backup is made there, protected by a password derived from `encryption_key`, and never passes through NATS; NATS holds the manifest that names it and the folders of the configuration folder. The backup before the previous one is deleted. A new leader reloads the backups of its Supervisor and restores from that storage. That is the route for databases (MariaDB, InfluxDB), media libraries and anything above the NATS limit.
* **Mosquitto and the MQTT entry.** The MQTT entry made by Supervisor discovery connects to `core-mosquitto`, the broker of the host it runs on, with the credentials the Mosquitto add-on generated once and keeps in its `/data`. Restoring that add-on's backup gives the new host's broker the same credentials, so the replicated entry connects there. Messages retained in the broker are as old as the snapshot; Zigbee2MQTT publishes its devices and their states again when it starts.

What this needs:

* Supervisor on every node. Without a Supervisor token the gate does nothing.
* The add-ons' repositories on every node (Zigbee2MQTT's, Music Assistant's): a restore installs a missing add-on from its repository. Whether Supervisor adds a missing repository from the backup was not checked.
* Hardware on the network, not on a host: a **network coordinator** for Zigbee (SLZB-06 and the like), a Z-Wave or Thread radio on the network, network cameras. A USB radio is tied to one host. If the coordinator can be set to accept one client at a time, do so: then the hardware refuses a second Zigbee2MQTT even where the cluster cannot know (the dead-Home-Assistant case above).
* An address that follows the leader for whatever connects **to** an add-on: MQTT devices (Tasmota, Shelly, ESPHome over MQTT) that connect to the broker's IP, Music Assistant players, a browser on an add-on's port. After a failover the add-on listens on the new leader's IP. See [An address that follows the leader](#an-address-that-follows-the-leader).

What it does not do:

* **A crash loses what changed since the last snapshot**: a device paired or renamed a few minutes before the leader died is not in the new leader's Zigbee2MQTT database (the device is still in the coordinator's network); a database add-on comes back with the data of its snapshot. A planned handover loses nothing only if its final snapshot succeeds: if Supervisor's backup fails or takes longer than the handover's 80 s, the next leader restores the last periodic snapshot.
* **No leader, no add-on.** While NATS is down every node fences itself (see the NATS limitation), so no node runs the managed add-ons: Zigbee is down with NATS. A node that cannot reach NATS when it starts (Home Assistant restarted, its add-ons ran on) stops its managed add-ons at once, through Supervisor, while it keeps trying to connect.
* `replicate: false` add-ons are only started and stopped: the leader starts them with whatever data it has. Never use it for Zigbee2MQTT.
* Add-ons that are not managed keep running wherever they run, on every node.
* What an add-on does after a restore is its own: Zigbee2MQTT and Mosquitto were looked at here, other add-ons (Music Assistant, the Matter server, OpenThread Border Router) were not tested.
* **Supervisor discovery is per host.** An add-on that offers an integration through Supervisor discovery (Mosquitto offers MQTT) registers a discovery message with the Supervisor of the host it starts on, and each Supervisor gives it its own id (it is not part of the add-on's backup). After a failover the new host's Supervisor announces the add-on again under a new id. MQTT allows one entry and keys nothing by that id, so the announcement is dropped; an integration that keys its entry by the discovery id may offer a second entry, or remove its entry when the old host's Supervisor withdraws the old id. Not tested against a real Supervisor.
* **Not tested against a real Supervisor at all.** The gate was tested against a fake one: the requests follow Supervisor's API documentation (the upload's form field name was not checked). It calls `http://supervisor` with the token itself rather than through the `hassio` integration's `aiohasupervisor` client, because it runs before integrations are set up (the cluster starts in bootstrap, the `hassio` integration later) and because the watchdog must stop add-ons without the event loop. Moving it onto `aiohasupervisor` once the client is available is a cleanup still to do.
* A managed add-on is down from the failover until it runs on the new leader: `addon_takeover_wait` after a crash (or until the old node reports it stopped, after a planned handover), plus the restore.

### An address that follows the leader

Everything that connects **to** Home Assistant goes to an address: the UI and the app, webhooks, an alarm panel that reports over SIA, devices that send to HA's IP, and MQTT devices that connect to the broker of a managed add-on. Only the leader runs the entries and add-ons that listen there, so that address must follow the leader. The cluster does not manage addresses; it tells whoever does:

```
GET /api/cluster/leader   ->  200 {"leader": true}    on the leader
                              503 {"leader": false}   on every other node
```

The answer needs no authentication (health checks of proxies and VRRP daemons cannot log in) and says nothing but whether this node leads. A node answers `503` while it is not connected to NATS, while it waits for the lease, while its promotion sets up the clustered entries (one after another: minutes on a large installation), and from the moment it starts to shut down, before it lets go of the lease. The new leader answers `200` once its promotion has been through every clustered entry and no setup it started (also those the renewal tick starts for entries that were waiting) still runs, so traffic does not move to a host that does not listen yet. An entry whose setup failed or is retried later does not hold it back: the endpoint says the promotion is done, not that every integration works; during a failover no node answers `200` for that time. Managed add-ons are restored and started in the background once the node leads, so Mosquitto can still be starting when the leader answers `200` (MQTT clients reconnect). `HEAD` gives the same status without a body.

* **keepalived (a virtual IP):** on every HA host, a `vrrp_script` that runs `curl -fsS -o /dev/null http://127.0.0.1:8123/api/cluster/leader` every second, with `weight` larger than the difference of the priorities, so that only the leader holds the address. Point DNS, the app, the alarm panel and the MQTT devices at that address. On HA OS, keepalived runs on another machine (the NATS hosts, a router) that checks both HA hosts, or as an add-on in `local_addons`.
* **HAProxy:** `option httpchk GET /api/cluster/leader` and `http-check expect status 200` in a backend with both hosts; for MQTT a `mode tcp` frontend on 1883 with the same HTTP check (`check port 8123`) against port 1883 of the hosts.
* **Traefik:** a load balancer service with both hosts and `healthCheck: { path: /api/cluster/leader, interval: 2s }`.

A check every second or two adds that much to the failover; the rest is the lease, the grace and the setup of the entries (see [Failover time](#failover-time)).

### Timing settings

* `lease_ttl`, `renew_interval` and `unload_grace` **must be the same on every node.** A node that finds a lease bucket with another TTL uses the bucket's TTL. Each node advertises its `unload_grace`; a node that sees a different one logs a warning and waits for the larger one when it takes over. `renew_interval` is not checked.
* A leader fences itself `fence_after = lease_ttl - max(0.6 * renew_interval, 0.2 * lease_ttl, 0.5)` seconds after its last renewal (2.4 s at the defaults, 8 s at a TTL of 10 s). From then it has `(lease_ttl - fence_after) + unload_grace` seconds to unload everything: **2.6 s at the defaults**, 4 s at a TTL of 10 s.
* An integration whose unload takes longer than that is ended by the watchdog (see section 3). That is deliberate: the alternative is two nodes running the same device.
* **Event loop stall limit:** if the event loop of the leader does not renew the lease for `lease_ttl + unload_grace - 0.3 s` (4.7 s at the defaults), the watchdog ends the process. Use a `lease_ttl` of **10 s or more on real hardware** (Raspberry Pi class devices, SD cards, busy instances): the stall limit becomes 11.7 s, at the price of a slower failover (see below).
* A node that boots into an empty lease bucket, or sees the bucket recreated, waits `lease_ttl + unload_grace` from when it started to watch the bucket before it can lead, because it cannot know whether an earlier leader is still running. A leader whose own key vanished with the bucket creates it again without waiting; a leader that is partitioned at that moment is not covered by this.

### Failover time

The end-to-end harness (two Home Assistant processes, one NATS server, `docker network disconnect` of the leader) measured at the defaults (`lease_ttl` 3 s, `renew_interval` 1 s, `unload_grace` 2 s), in 10 runs: the lease moved after a median of 2.9 s (2.7 to 5.6 s), and the first state of the new leader's `sun` entry arrived after a median of 4.9 s (4.6 to 7.7 s; the slowest run was probably disturbed by other work on the host, which was not checked). That is one config entry and one machine. The time depends on `lease_ttl + unload_grace`, the election tick, and how long each integration takes to set up (the entries are set up one after another). A clean release (a shutdown or step-down in which everything unloaded) hands over without the grace. Nothing here was measured on ARM hardware or with a three-server NATS cluster.

**A real installation takes much longer.** After the lease and the grace, a promotion sets up the clustered entries one after another, so the failover lasts about as long as all their setups added together. Settings → System → Repairs → ⋮ → *Integration startup time* shows each integration's setup time, but measured at boot, where the entries of one integration start at the same time: in a failover an integration with many entries costs about one setup per entry. An entry that waits for a device until a timeout (an unreachable camera) delays every entry after it. As an example, one installation with 146 clustered entries in 50 integrations showed 81 s of setup time at boot, in total; one integration had 18 entries (14 s at boot), another 27. Set up one after another, that is an estimate of **2 to 3 minutes** until every entry runs, longer than its normal boot, which sets them up in parallel. This is an estimate from the boot times, not a measured failover. Setting entries up in parallel during a promotion, or the most important ones first, is not implemented. Managed add-ons start in the background, apart from the entries: after a crash `addon_takeover_wait` (90 s) plus the restore of their snapshot (a different add-on version adds its download).

## 6. Known limitations

* **Registries follow the leader at takeover, not live.** A registry change is mirrored when its store is written: up to 10 s after the change while Home Assistant runs, and at a clean shutdown. A change made in the last seconds before a crash is lost. A standby shows its own registries until it takes over.
* **A large registry, or a large config entry, is not mirrored.** A registry larger than the NATS `max_payload` (1 MB by default) is not mirrored, and an earlier, smaller copy is deleted, so the new leader keeps its own (a warning says so). An entry record larger than that is reported once as an error and not replicated. If an earlier, smaller record of the entry exists, it is replaced by a small marker, because a node that took the entry over from the old record would run it with out-of-date data (a token that was rotated since): a promotion then stops with a message naming the record, the node gives the lease up and raises the repair issue *Cluster node cannot take over*, until `max_payload` is raised or the entry is smaller again. A registry or a UI file that is too large leaves a node with its own data; a large entry stops a takeover. Raise `max_payload` in the NATS server configuration (for example `max_payload: 8MB`).
* **Areas, floors, labels and categories created on a standby are replaced by the leader's** at takeover. An entry created by a config flow on a standby stays local until that node leads: make configuration changes on the leader. A standby refuses to remove a clustered entry (the removal runs the integration's clean-up, which can revoke credentials the leader uses); remove it on the leader. A standby also refuses to open an options flow, to start a reauthentication or reconfiguration, and to disable or enable a clustered entry (`ConfigEntryPlacement.async_refuse_change`; the error names the leader): such a change would be **reverted** when the node takes over, because the leader's record is applied without comparing versions, and a reauthentication done on a standby would be lost at the next failover. The leader's own change, applied on a standby, is let through. Changes that the placement does not see (a change of subentries from the UI, a service that updates an entry) are not refused. Make every change on the leader.
* **History, logbook and statistics are per node.** The recorder runs on every node and writes to that node's own database (`home-assistant_v2.db` is not in `.storage` and is not replicated). A standby records the states it mirrors, so its history follows the leader's while it is connected; a failover, a standby that was down, or the seconds before a crash leave gaps that differ per node, and long-term statistics (energy) are compiled by each node from its own data. Pointing two nodes at one MariaDB or PostgreSQL database (`db_url`) is not supported: both would write the same states and compile the same statistics.
* **Home Assistant Cloud stays on each node.** `cloud` is a `system` integration and `.storage/cloud` is private: each node logs in on its own, or not at all. Its remote UI, cloud webhooks and the Alexa and Google Assistant links reach whichever node is connected, not necessarily the leader. A voice command that arrives on a standby becomes a service call, which is forwarded to the leader; a webhook for a clustered entry has no handler on a standby. Whether one Nabu Casa account may be connected from two nodes at once was not checked, and none of this was tested.
* **Integrations of type `system` run on every node.** Their config entries and their YAML or discovery platforms are not clustered, and their entities' states are not mirrored (`helpers/cluster.py`). In 2026.11 that is 95 integrations: Core's own infrastructure (`http`, `frontend`, `recorder`, `history`, `logbook`, `energy`, `network`, `bluetooth_adapters`, `usb`, ...); **`cloud`** (Home Assistant Cloud: each node logs in on its own, its `.storage/cloud` is private, see *Home Assistant Cloud stays on each node*); `alexa` and `google_assistant` set up from each node's own YAML; `unifi_discovery`; the legacy notify platforms `telegram` and `msteams` (senders: a call to them is a service call like any other); and stubs of removed integrations (`konnected`, `sunweg`, `myq`, ...) that only raise a repair issue. A `system` integration that does work for the house would run on every node at once; none of those checked in 2026.11 does (not all 95 were checked), and the list is the integrations', not the cluster's, and can change.
* **Credentials and users stay on each node.** Private stores are never mirrored: users, refresh tokens, password hashes, MFA secrets, onboarding, and the core configuration (location, units). Each node has its own users; log in to each node. Application credentials (OAuth client ids and secrets) are not mirrored either: configure the same ones on every node. A node that takes over an OAuth entry whose application credential it lacks raises a repair issue naming it.
* **Config entry records are published after the change, not with it.** A former leader cannot overwrite them once another node started its term, but what it had not published is lost. A change is published as soon as it is made (the debug log shows how many milliseconds later); a crash of the leader after an integration rotated a token (and the provider invalidated the old one) but within that window leaves the next leader with the old token. When the integration then asks for reauthentication within 10 minutes of a takeover, a repair issue explains why.
* **Losing the storage bucket loses the tombstones, not the removals.** After the `hass_storage` bucket is recreated, the leader publishes its live entries and an inventory again: the entries it runs and the latest 256 removals, from a log each node keeps in a private store. A node that takes over removes the entries it knows from the cluster that the inventory lists as removed, or that neither the inventory nor any record shows any more. Entries made on that node only are kept. If no inventory exists although the node saw one before (the bucket was lost and no leader republished it), it keeps all its entries and raises a repair issue asking you to check for removed integrations.
* **A takeover applies the leader's data one part at a time.** Entry records, then the registries, then the UI files and helpers. A record whose content is wrong (malformed, an unexpected shape) is skipped with an error in the log: it would be wrong on every retry. Any other failure (a file that cannot be written, a time-out, an error of Core) stops the promotion: the node gives the lease up, waits out a cool-down, and another node (or this one) tries again. The same holds for an exception anywhere in a promotion, and for a pre-setup step of an entry (credential check, state adoption) that failed: the entry stays on standby. So a record that fails for a reason on every node leaves the cluster without a leader, and the log says why.
* **A UI file the leader deletes is deleted on the standbys.** A deletion record is published once the leader noticed the file is gone (within a second, while it leads). A file that was never there when a node became leader is not announced as deleted.
* **Restore state is a checkpoint.** The general restore state is saved every 15 minutes and at shutdown; after a crash the new leader restores from the last checkpoint that was published. A checkpoint that cannot be read at a takeover (a time-out) stops the promotion and is tried again after the cool-down; one that was read but cannot be used is skipped with a warning. UI helpers publish their state on every change.
* **Integrations without config entries and without entity platforms run on every node.** Top-level YAML integrations (`graphite:`, `mqtt_statestream:`, ...) see the mirrored states as ordinary state changes and act on every node; configure them on one node only.
* **A recreated NATS stream starts above the old one.** A compare-and-set condition names a sequence, and a stream created under the same name would repeat the old numbers. A node creates its buckets with a first sequence taken from the clock (milliseconds), so a condition sent to the old stream cannot be satisfied by the new one. Two nodes that race to create a bucket end up with one stream; the loser binds to it.
* **A forwarded call carries the caller's role, not the caller.** The sender checks the entities the caller selected against its own registry; the leader expands the selection against its own and runs the call as its system user of that role. Built-in roles are unrestricted for entity control, so this is equivalent for them; a custom permission policy that restricts entities is not preserved across nodes. Members of a cluster trust each other: the NATS permissions bind the subjects each node may publish, and a node answers each call it receives once (`allow_responses: { max: 1 }`). The JetStream API is limited to the three KV streams (and the two read-only calls about the account: its info and its stream names); every member can still write them.
* **Recovery mode without evidence.** Recovery mode keeps clustered entries unloaded if the configuration names a cluster (also when recovery mode was requested explicitly) or if this node ever started as a member (`.storage/cluster`, written before the cluster is set up). If the configuration cannot be read and this node never started as a member, the text of `configuration.yaml` is searched for a top-level `cluster:` line, and a node that has it is treated as a member. Only a node with none of the three pieces of evidence is treated as stand-alone.
* **A lost bucket still loses data that no node holds.** The recovery republish covers live entries, the inventory and current UI data. The recovery republish also publishes the saved file of every mirrored store, so unchanged registries and restore state are included. A node that lost the last authoritative copy together with the bucket can promote entries that were removed meanwhile (a repair issue says so when it remembers an inventory).
* **Managed add-ons rely on what each node reports.** A node whose Home Assistant died while its host and its add-ons run on cannot report, and cannot be stopped from another node; the new leader waits `addon_takeover_wait` for it and then starts the add-on (see [Supervisor add-ons](#supervisor-add-ons-apps)). If that Home Assistant does not come back within the wait, both run. A coordinator that accepts one client closes this for Zigbee2MQTT.
* **Add-ons that are not managed do not fail over.** A broker or bridge that runs as an add-on next to the leader and is not in `managed_addons` stops with that host, and an entry that Supervisor discovery made for it (`source: hassio`) reaches the new host's own add-on, without the data. Manage it, or run it outside the cluster's hosts. A crash loses the changes of a managed add-on since its last snapshot.
* **Connections from outside go to an address, not to the leader.** Integrations that HA connects to (polling, a tunnel, a client connection) follow the leader without changes: the new leader opens its own connection. Integrations that something else connects to do not: an alarm panel that reports to an IP and port (SIA), a device or a service that sends to HA's address, a webhook. A clustered entry runs only on the leader, so a standby does not listen for it, and the cluster does not forward HTTP requests or other inbound connections. Such integrations need an address that follows the leader (a virtual IP, a reverse proxy, DNS) or a sender that can report to more than one receiver. The same holds for the address users open in a browser or the app. The cluster does not manage addresses; `GET /api/cluster/leader` tells a proxy or a VRRP daemon which node leads (see [An address that follows the leader](#an-address-that-follows-the-leader)).
* **A failover sets the entries up one after another.** See [Failover time](#failover-time): on a large installation this takes minutes, not seconds, and the order of the entries decides when the important ones run.
* **The NATS deployment is part of the trust boundary.** The bucket and subject names are fixed: give each cluster its own NATS account (or server), and each node its own user with the permissions of [Securing the NATS server](#securing-the-nats-server). Without those permissions any client of the account can claim to be any node. Even with them, a member can call services as an admin (the role in a forwarded call is the caller's, and the receiver cannot check it) and write the cluster's records, and every member holds the `encryption_key`: treat every node as trusted with the secrets of the whole installation. The NATS server, its disk and its backups hold the entry records only as ciphertext, but they still hold everything else the cluster replicates (registries, UI files, helper states). A forwarded call carries the caller's user and a role ceiling, not custom permission policies. A call whose body does not name the sender and the run of that node that is a member now is refused.
* **Nodes must run the same Home Assistant version.** Every member key and the lease carry `ha_version` (`homeassistant.const.__version__`); a node that sees a live node with another version logs a warning and raises the repair issue `cluster_version_mismatch` (below), which goes away when every node is on the same version. It only warns: refusing to take over would leave a cluster without a leader in the middle of an upgrade. A node that does not write the field (from before it existed) is not counted. A leader whose registry storage version differs is not loaded (a warning says so), and the protocol version still blocks a takeover (section 10).
* **YAML platforms run on the leader only.** A platform configured in YAML (`climate: - platform: generic_thermostat`) or loaded by discovery is set up on the leader only; the standbys mirror its entities and set it up when they take over. A standby keeps the YAML it read when it started: after changing YAML platforms, reload on the leader and restart the standbys. Entities that an integration adds to its own domain from YAML (`input_boolean:`, `timer:`, `alert:`) still exist once per node with separate state; for helpers made in the UI see the notes below.
* **A takeover replaces registries without events.** The registries are loaded from the leader's copy before any clustered entry starts, by running the registry's load again; no `*_registry_updated` event fires for what changed. Integrations that run on every instance (and read a registry before the takeover) do not see those changes until they read it again.
* **Helper state costs a write per change.** Every state change of a UI helper (input_boolean, counter, timer, ...) is published to the disk-backed `hass_storage` bucket, so the leader's NATS server writes to its disk as often as a helper changes. Keep fast-changing counters out of UI helpers on a node with an SD card.
* **A shutdown during a promotion** cancels the promotion; an entry that was already set up is unloaded by the shutdown like any other, and a promotion that was cancelled does not give the lease up cleanly, so the other nodes wait for it to expire.
* **The NATS client is used beyond its public API.** The watchers and the close use attributes of `nats-py` that are not documented (`_subs`, `_transport`, the KV watcher's subscription). The version is pinned; check these when it is raised.
* **A refusal is recognized by its text.** nats-py reports a refused conditional write as an error code and a description, the sequence the server saw is read from the description.
* **Make UI changes on the leader.** Automations, scripts, scenes and UI helpers made in the leader's UI follow on every node. The same change made in a standby's UI stays on that node and is replaced by the leader's next change.
* **Only the UI files are synced.** `automations.yaml`, `scripts.yaml` and `scenes.yaml` are; other YAML is not: packages, other included files, `secrets.yaml`, and blueprints (an automation made from a blueprint needs the blueprint file on every node). A UI file or a helper collection larger than the NATS `max_payload` is not synced (a warning says so).
* **A standby shows its own state of UI helpers.** Helper entities exist on every node; a standby forwards their service calls to the leader and keeps its own copy's value. At a failover the new leader takes each helper's last state on the old leader (published on every change, so also after a crash), applied as a restart would: a helper with an `initial` value starts at it, a `timer` without `restore: true` is idle.
* **Registry settings of UI automations, scripts, scenes and helpers stay per node.** Their entity id, name, area, labels and categories set on the leader follow the rule for entities without a config entry: the new leader keeps its own. A person's link to a user refers to the leader's user ids; users are not synced.
